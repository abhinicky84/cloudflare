Branches

main is production, and the base for all new work. Protected, and tagged on every release.

staging is the QA environment. Everything waiting for sign-off is deployed here. Nothing is released from staging: it is a proving ground, not a release branch.

Ticket branch, feature/OCTV-12-top-navigation. One per Linear parent ticket, cut from main. It is the assembly point for the whole feature.

Sub-task branch, feature/OCTV-123-top-navigation-frontend. One per Linear sub-ticket, cut from the ticket branch, always ending with the discipline: frontend, contentful, backend, qa, analytics or content.

Also bugfix/OCTV-456-short-description, hotfix/OCTV-789-short-description and chore/OCTV-321-short-description.

The flow

  1. Break the parent ticket into discipline sub-tickets, and create the ticket branch from main once, before any work starts.
  2. Each person works on their own sub-task branch and raises a PR into the ticket branch. One approval from the same discipline, CI green, squash merge.
  3. When all sub-tasks are in, deploy the ticket branch to its own preview and review the whole feature there with product, design, content and QA. Fixes come back as new sub-tickets, never as direct pushes.
  4. PR the ticket branch into staging. Staging deploys automatically; QA runs the full pass there.
  5. One named feature reviewer then does the overall review on staging: QA results, acceptance criteria, use cases and a sanity sweep of the whole impacted area. They record approval on the Linear ticket and move it to Ready for Release.
  6. When the business is ready to release, PR the same ticket branch into main, with two approvals. Merge, tag, and trigger the production deployment.
  7. Delete the ticket branch and its sub-task branches.

Merge and sync rules

  • Sub-task into ticket branch: squash.
  • Ticket into staging, and ticket into main: merge commit, no fast-forward.
  • Rebase only your own sub-task branch. Never rebase staging, main, or a shared ticket branch.
  • Rebase your sub-task onto the ticket branch daily, and merge main into the ticket branch every couple of days before either promoting PR.
  • Nothing is promoted while its pipeline is red.

Keeping staging honest

Staging collects work that has not shipped yet, so it drifts from production. Reset it from main after every release, so each cycle starts as a true copy of production plus only the features currently under test. Staging is never the source of a release, and nothing is ever merged from staging back into a ticket branch.

Approval gates

Promotion Gate
Sub-task into ticket branch One discipline approval, CI green, preview deployed.
Ticket into staging One maintainer approval, all sub-tickets Done, and the full-feature review recorded on the ticket.
Ticket into main Two approvals with at least one lead, QA passed on staging, and the feature reviewer approval recorded on the ticket.

Hotfixes

Cut hotfix/OCTV-789-short-description from main, for production-impacting defects only. Narrowest possible fix plus a regression test, two approvals, merge to main, deploy. Merge main into staging and into every open ticket branch the same day.

Bugs

Where you branch from depends on where the bug was found.

  • Still in a sub-task PR: keep pushing to that branch.
  • Found in the ticket-branch review: a new sub-task branch off the ticket branch.
  • Found on staging during QA: fix it on the ticket branch that introduced it and re-merge that branch into staging. The ticket branch is still open, so there is nowhere else the fix should go.
  • Found on staging but belonging to no open ticket: a bugfix branch off main, through the same flow.
  • Found in production and urgent: it is a hotfix.

Linear

Copy branch names from Linear so the tickets auto-link. Automatic transitions: In Progress on branch push, In Review on PR open, Ready for QA when the code reaches staging, Released on the production tag. Manual: QA Passed, recorded by QA with the build SHA, and Ready for Release, recorded by the feature reviewer.

Scripts

Branches are created by the repository script, never by hand.

Creating a branch: always npm run branch, never git switch -c. The script is what keeps names compliant, so every branch links back to its OCTV ticket automatically. This applies to ticket, sub-task, bugfix, hotfix and chore branches alike.

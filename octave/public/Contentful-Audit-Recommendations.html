01

Executive summary

The Octave Contentful space implements a governed, component-based marketing site architecture using a decoupled page-builder pattern alongside a paired resource-library model. The naming taxonomy (BM/BT/MA/DC/GN/GF/BS/UT prefixes) and the use of link-indirection primitives (UT2–UT5) represent strong content-model discipline.

The audit surfaces several structural risks, most notably a dual asset system (native Contentful assets versus Frontify JSON fields), untyped JSON fields, environment sprawl, and repeated field shapes across resource and article-like content types that should be consolidated. This report details findings by severity, highlights their specific impacts on website performance, content authoring, and technical maintenance, and provides concrete remediation guidance.

02

Critical issues

Highest risk of data inconsistency and rendering failure at scale. These carry ambiguity into production, where the cost is a broken page rather than a slow workflow.

Critical Finding 01

Dual asset systems: native assets vs. Frontify JSON

Finding

Many content types carry both a native Contentful asset field (e.g. backgroundImage) and a parallel Frontify v2 JSON object field (e.g. backgroundImage Frontify). Native fields are often disabled but still present in the schema, likely retained for legacy entries.

Risk
  • Editors and API consumers cannot reliably determine which field is authoritative for a given entry.
  • Front-end rendering logic must branch conditionally (if frontifyImage else if legacyImage), increasing complexity and bug surface.
  • Migrations become error-prone when two competing sources of truth exist.

Content authoring & editorial experience

Editors face constant confusion over active versus inactive fields, leading to double data entry, broken page previews, or publishing media into deprecated native fields.

Website performance & reliability

Conditional branching in rendering logic inflates client JS bundles and increases evaluation overhead, while missing fallback checks risk rendering broken or missing image tags on live pages.

Technical maintenance & scalability

Data migrations are highly error-prone without a single source of truth, forcing developers to build and maintain defensive fallback parsing across all consuming applications.

Recommendation
  • Fully deprecate and remove native asset fields where Frontify is now the standard, migrating any legacy data via script.
  • If both must coexist temporarily, document in the field descriptions which field is authoritative, and enforce it with required-field validation.
Open question for the teamWhy are we using both Contentful Asset Management and Frontify Asset Management?
Critical Finding 02

JSON object fields masquerading as structured data

Finding

Frontify integration fields (frontifyFile, frontifyVideo, imageFrontify, and others) are implemented as generic JSON object fields rather than a validated, structured field type.

Risk
  • No schema validation, reference integrity, or self-documentation within Contentful.
  • Any arbitrary JSON can be written to these fields.
  • If Frontify's payload shape changes, nothing in Contentful will catch the mismatch.

Content authoring & editorial experience

Authors receive no real-time validation or inline guidance in Contentful. Invalid or malformed JSON payloads save without warning, leaving authors unaware until components fail on live pages.

Website performance & reliability

Missing keys or structure changes in raw JSON objects trigger unhandled runtime JavaScript exceptions, causing unrendered media components or full white-screen page crashes.

Technical maintenance & scalability

Contentful cannot enforce reference integrity. Any API or payload shape change from Frontify bypasses validation completely, requiring custom parsing guards in downstream code.

Recommendation
  • Use Frontify's App SDK field validation, if available, rather than raw JSON object fields.
  • At minimum, document the expected JSON shape explicitly in field descriptions for editor and developer clarity.
Critical Finding 03

Insufficient reference & circular-reference guardrails

Finding

The blocks array accepts references to roughly 30 different content types; UT2 Internal Link accepts references to roughly 22 content types. Combined with the Deep Clone app, this creates potential for deeply nested or circular reference chains.

Risk
  • A block referencing a Page via UT2, where that Page embeds the same block, could create runaway clone trees or rendering loops.
  • Performance degradation on deeply nested pages.

Content authoring & editorial experience

Sifting through ~30 block choices slows down daily editing. Using Deep Clone on deeply nested blocks can accidentally clone runaway trees, duplicating dozens of unwanted entries.

Website performance & reliability

Circular or deeply recursive page references cause infinite loops in GraphQL/REST API queries or server-side rendering, leading to site build timeouts, elevated TTFB, or site-wide downtime.

Technical maintenance & scalability

Deeply nested payloads degrade query speeds, bloat API response sizes, and make automated content migrations extremely risky to execute.

Recommendation
  • Tighten "Accepted content types" validations on all reference fields rather than allowing broad or any-entry links.
  • Stress-test Deep Clone against deeply nested, real-world page structures to find loop and performance issues before production does.
03

Moderate concerns

These rarely break a page outright. They tax every schema change, every release, and every editor who moves between similar entry forms — and the cost compounds as the space grows.

Moderate Finding 04

Environment sprawl with no lifecycle policy

Finding

Multiple dated snapshot environments exist without a visible deletion policy, including content-for-staging, production-5-14-26-1446, master-test-transform-6-30-26, production-7-1-26, and production-7726-1239.

Risk

Contentful enforces a maximum number of environments per space, depending on plan. Continued accumulation will eventually block creation of new environments needed for legitimate work.

Content authoring & editorial experience

Authors risk logging into stale snapshot environments by mistake, wasting hours creating or editing content in non-production environments that is then permanently lost.

Website performance & reliability

Hitting Contentful environment limits blocks developer staging environments, halting urgent release pipelines and hotfixes from reaching production.

Technical maintenance & scalability

Accumulating obsolete snapshots prevents automated CI/CD branch environment creation and schema migration testing.

Recommendation
  • Implement a TTL/cleanup policy: export and delete snapshot environments after a defined period, for example 30–60 days.
  • Document the purpose of each snapshot environment at creation time so its lifecycle owner is clear.
Moderate Finding 05

Duplicate field shapes across content types

Finding

Event Detail, Press Release, and Resource: Blog Page independently repeat the same field shape: eyebrow, headline, cta, textLinks, author, date, postBody, SEO fields, and card display fields.

Risk

Every schema change — adding an updatedDate field, for instance — must be replicated manually across three to four or more content types, increasing the likelihood of schema drift and an inconsistent editorial experience.

Content authoring & editorial experience

Editors face subtle inconsistencies across similar entry forms, increasing operational confusion and error rates when moving between content types.

Website performance & reliability

Front-end teams must write duplicate rendering components and query logic, inflating client-side bundle sizes and causing inconsistent SEO meta tag generation.

Technical maintenance & scalability

Routine schema updates require tedious manual replication across multiple content types, significantly increasing development overhead and schema drift risk.

Recommendation
  • Since Contentful lacks true type inheritance, extract shared field groups into linked component entries where feasible — for example an SEO Metadata entry type referenced by all page and article types, instead of inlining six or more SEO fields everywhere.
  • This is a widely recommended Contentful best practice for large multi-type spaces.
Moderate Finding 06

Card metadata duplication in the resource Page + File pairing

Finding

Both *Page and *File types in the resource library independently carry card metadata: title, description, and image.

Risk

Ambiguity over which entity is authoritative for card rendering in DC1/DC2 dynamic blocks, and a risk of inconsistent data if both are edited independently.

Content authoring & editorial experience

Authors must update identical card fields in two separate entries; changing one without the other immediately creates data drift and confusion.

Website performance & reliability

Dynamic grid components (DC1/DC2) render mismatched titles or images on the live site, degrading visual polish and brand trust.

Technical maintenance & scalability

Engineers must write complex fallback logic such as Page.cardImage ?? File.cardImage, complicating GraphQL queries and increasing card listing payloads.

Recommendation

Explicitly designate one entity — recommended: the Page type — as the canonical source for card rendering, and document this in field descriptions and internal governance docs.

Moderate Finding 07

Long manual enums create scaling friction

Finding

Several fields use long hardcoded enums that require ongoing maintenance: contentSelection on DC1/DC2 dynamic blocks, productOfInterest on the GF Sales Form, and the UT2 Internal Link target type list of roughly 22 content types.

Risk

Enum values require a content-model migration and deploy to update, unlike reference fields, which editors can manage directly.

Content authoring & editorial experience

Authors are restricted by rigid static dropdowns and cannot select newly created categories or products until a developer deploys a schema migration.

Website performance & reliability

Mismatches between static enum options and dynamic content types cause empty listing components or misrouted form submissions in production.

Technical maintenance & scalability

Even simple routine additions, such as adding one product selection option, require developer code changes, migration scripts, and deployment cycles.

Recommendation

Where feasible, replace hardcoded string enums with reference fields to dedicated entities — a Product or Resource Type content type, for example — allowing editors to add new options without a schema change.

04

Strengths worth preserving

Remediation should not disturb these. They are the reason the space scales as well as it does today.

UT link indirection

Avoids hardcoded URLs and enables centralized link management. An excellent, scalable pattern.

Prefix taxonomy (BM/BT/MA/DC/GN/GF/BS/UT)

Significantly aids discoverability across a large space with 30+ block types.

Enum-driven dynamic content

contentSelection on DC1/DC2 reduces the manual curation burden for editors.

Deep Clone scoped to 4 top-level types

Page, Hybrid Page, Legal Page, and Resource: Case Study Page only — a sensible scope that avoids uncontrolled clone sprawl.

Merge app for cross-environment schema diffing

An appropriate tooling choice for a multi-environment setup at this scale.

Page + File pairing for resources

Clean separation between SEO-rich landing pages and downloadable or embeddable file assets.

Conclusion

Sound architecture, ambiguous edges

The Octave Contentful space is architecturally sound and reflects mature content-modeling practices for a large, multi-locale marketing site. The priority for the team should be resolving the dual asset-field pattern and the untyped JSON fields, as these carry the highest risk of data inconsistency and rendering bugs at scale.

Addressing environment sprawl and field-shape duplication next will reduce long-term maintenance overhead and improve editorial consistency across the ~40+ content types in this space.

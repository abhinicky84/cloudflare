Contentful ↔ Frontify
Integration Options & Estimates

Our current setup (Option 1) blocks anyone without a personal Frontify seat from browsing assets inside Contentful. We are evaluating alternative connections specifically to avoid setting up multiple paid Frontify accounts, as scaling seats across the entire authoring team is not commercially realistic — Frontify licensing is per-user, not open source, and would meaningfully raise cost.

The three options evaluated

Option 1: Frontify V2 — External App (Current Setup)

Not listed on the Contentful Marketplace, so it's added manually via App Definition → External App. Uses Frontify Finder v2 with per-user login.
✓ Pros
  • Latest Frontify integration, current UI and full asset metadata support
  • Native per-user Frontify login — respects each person's own permission scope (private libraries, download-protected assets) automatically
  • Direct vendor-maintained connection, actively supported by Frontify
✗ Cons
  • Cost: every author needs a paid Frontify seat — not viable to license the whole authoring team just so they can pick assets in Contentful
  • Writers/Editors without a seat can't preview or select assets — exactly the problem we're solving for
  • Onboarding friction — IT has to provision a licensed seat per author
  • Not marketplace-listed, so setup and updates are manual

Option 2: Frontify — Marketplace App (v1 / legacy)

Installed from the Contentful Marketplace, authenticated with a single Frontify Access Token — typically the Media Library's own token.
Status: Deprecated for new customers since Q4 2024. Frontify's own docs say it's no longer offered to any additional customers, and enabling it likely requires going through a Frontify Customer Success Manager rather than a self-serve Marketplace install.
✓ Pros
  • No per-seat cost — one shared Access Token covers the whole DAM, so no additional Frontify licensing needed for authors
  • Any Contentful role (Author, Writer, Admin) can browse and select assets, no personal Frontify login required
  • Same field type (JSON object) as V2, so the existing field can potentially be reused as-is
  • No custom code to build or maintain — it's a pre-built app
✗ Cons
  • Deprecated — long-term support and roadmap are uncertain, and Frontify may retire it entirely
  • Token is shared/global, so per-user access nuance (private libraries, download-protection approval) is lost — anything the token can reach, every author can reach
  • Exact field payload shape isn't publicly documented — needs to be verified against what V2 currently writes, to confirm the frontend doesn't need changes

Option 3: Custom App on Frontify's API

A self-built Contentful App (App SDK) that talks to Frontify's GraphQL API directly through one service-level credential, instead of the per-user Finder widget.
✓ Pros
  • No per-seat cost — one service-account/API token, not individual Frontify licenses
  • Full control over auth, UI, and exactly which Frontify features surface to authors
  • Not exposed to the legacy app's deprecation risk — built against Frontify's current, supported API
  • Can be scoped tightly to just "browse and select an asset," nothing extra
✗ Cons — the real bottlenecks
  • Setup effort: Requires approx. 67 hours total across Contentful, FE, and QA teams to build out the architecture for Frontify's GraphQL API, backend proxy, UI, and testing
  • Non-Open-Source API: Frontify's proprietary API requires mapping private GraphQL schemas and custom download permission rules
  • We own security for the service token, rate limiting against Frontify's API, and all future maintenance
  • Payload has to be hand-built to match V2's exact field shape, or the frontend needs updating too
How it would be built
  1. Contentful custom App (App SDK + Nuxt 3 UI) installed on the same JSON object field, replacing the Frontify Finder widget in the field editor.
  2. A backend/proxy (serverless API endpoint on Vercel) holding one Frontify Personal Access Token server-side — never in the frontend App code.
  3. Frontify's GraphQL API queried from that backend for libraries, projects, and asset search/thumbnails, returned to the App's UI.
  4. UI replicates Finder — search, browse, thumbnail grid, Select button — visible to every Contentful role, no personal Frontify login gate.
  5. On selection, write the field to match V2's existing shape (id, title, name, ext, height, width, created, generic_url, preview_url, src, metadataValues, focalPoint, pageCount, tags, copyright, licenses, description, type, appVersion) so the frontend needs zero changes.
  6. Download-protected assets: replicate Frontify's own rule — don't surface an asset as selectable unless the service account itself has been approved for it in Frontify.

Recommendation

Cost rules out Option 1 (Current Setup) for the whole authoring team, so the decision sits between Option 2: Legacy Marketplace App (~30-40 hrs total effort) and Option 3: Custom App on Frontify's API (~65-75 hrs total effort).

  1. Get the Frontify Access Token (or sandbox access to the legacy app) from the client first — feasibility is unconfirmed given the Q4 2024 deprecation, and nothing else should be decided before this test.
  2. If it installs and the field payload matches V2 closely enough — go with Option 2. It's the fastest, lowest-effort path (30 hrs) and needs no major engineering build.
  3. If it's blocked, unstable, or the payload diverges too much — fall back to Option 3 (Custom App, estimated at 67 hrs). It costs setup time, but it builds directly on supported APIs and permanently eliminates per-seat license dependencies.

Discovery Goals

Author Freedom, No IT Dependency

Design Philosophy

Design Approved Across Every Viewport

Viewport 01
🖥️
Desktop

Richest layout. Multi-column grids (1–4 columns), full visual hierarchy, expanded wizard navigation. Primary design canvas.

1280px and above
Viewport 02
⬜
Tablet

Adaptive transition. Columns collapse thoughtfully, touch patterns emerge, and spacing is recalibrated for medium screens.

768px – 1279px
Viewport 03
📱
Mobile

Most constrained, often most critical. Single-column, full-width inputs, simplified wizard flow, and finger-friendly controls.

375px – 767px
⚠️

Design sign-off is a prerequisite to build. Initial mockups set the direction — they are not a specification. Every component's visual treatment must be reviewed and formally approved across all three viewports before development begins.

Discovery Framework

Dimensions to Explore

💡

This is a starter list — not an exhaustive one. The 7 dimensions below are initial prompts to structure discovery. As conversations progress, more requirements, edge cases, and considerations will naturally surface. Capture everything.

01
📐

Component Rendering & Layouts

How does each component render in 1–4 column grids? How do checkboxes and radio groups display — vertical or horizontal? Layout rules per viewport?

02
🎨

Component Configuration Options

What can authors control per component — color, font, label styling, alignment? What is fixed by the design system vs. open for author customization?

03
🏗️

Template-Level Flexibility

Can authors set background colors or images? Full-bleed vs. 8-column grid? What layout variants exist at the template level?

04
🧭

Multi-Step Form Wizard

Is a wizard needed? If yes — vertical side rail or horizontal top bar for steps? Mobile behavior? Validation and navigation rules between steps?

05
📤

Submission & Data Flow

Supported endpoints: AEP, custom AWS URLs. Confirmation states, error handling, and redirect behavior per submission type.

06
⚡

Dynamic & Conditional Behaviors

Show/hide fields based on selections. Field dependencies, pre-fill from user profiles or URL params, context-based validation rules.

07
📋

Pre-Defined Data Sources

Which dropdowns need centrally managed lists? Who maintains them? How do authors reference them without developer help?

Collaboration Model

Who Does What

Roles are clear. Verticurl brings the approach and expertise. NFL brings the context, decisions, and ownership.

Verticurl

Collaborative Support & Approach
  • Define and share the discovery framework
  • Provide component inventory and capability thinking
  • Share initial design mockups for stakeholder alignment
  • Translate design decisions into AEM technical requirements
  • Guide component-level requirement definition with AEM best practices
  • Review and validate requirements as they are documented

NFL

Discovery Ownership & Delivery
  • Drive and own the discovery process end-to-end
  • Convene stakeholders — Marketing, Product, CMS/IT, Content
  • Evaluate components against actual NFL authoring use cases
  • Decide on configuration options, styling scope, and behaviors
  • Provide visual design sign-off across all three viewports
  • Document all outputs as JIRA stories with acceptance criteria
📋

Requirements live in JIRA. Every discovery decision — component behavior, template options, submission logic, dynamic rules — becomes a JIRA story with clear acceptance criteria. This is the build team's source of truth.
